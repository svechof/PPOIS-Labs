# Сборка, GitHub и защита лабораторной работы №1

## 1. Локальная сборка

Требуются CMake 3.20+, компилятор C++17 и Git. При первой конфигурации GoogleTest загружается через CMake `FetchContent`, поэтому нужен интернет.

```bash
cmake -S lab1 -B lab1/build -DCMAKE_BUILD_TYPE=Debug
cmake --build lab1/build --parallel
ctest --test-dir lab1/build --output-on-failure
./lab1/build/bin/lab1_cli
```

## 2. Санитайзеры

```bash
cmake -S lab1 -B lab1/build-asan -DCMAKE_BUILD_TYPE=Debug -DLAB1_SANITIZE=ON
cmake --build lab1/build-asan --parallel
ASAN_OPTIONS=detect_leaks=1:abort_on_error=1 UBSAN_OPTIONS=print_stacktrace=1:halt_on_error=1 ctest --test-dir lab1/build-asan --output-on-failure
```

ASan обнаруживает многие ошибки памяти, а UBSan — ряд видов неопределённого поведения. Эти проверки дополняют тесты, но не доказывают отсутствие всех дефектов.

## 3. Измерение покрытия

```bash
python3 -m pip install gcovr
cmake -S lab1 -B lab1/build-cov -DCMAKE_BUILD_TYPE=Debug -DLAB1_COVERAGE=ON
cmake --build lab1/build-cov --parallel
ctest --test-dir lab1/build-cov --output-on-failure
lab1/scripts/coverage.sh lab1/build-cov tic_tac_toe
lab1/scripts/coverage.sh lab1/build-cov polynomial
lab1/scripts/coverage.sh lab1/build-cov project
```

CI задаёт строгий порог более 90% (`90.01`). Если покрытие ниже этого значения, job падает; тесты нельзя заменять простым отключением проверки.

## 4. Проверки стиля и независимости

```bash
lab1/scripts/check_style.sh
lab1/scripts/check_independence.sh
```

`check_style.sh` проверяет запрещённые маркеры и конструкции, а `check_independence.sh` проверяет, что домены не подключают друг друга и не используют `std::cin`, `std::cout` или `std::cerr`.

## 5. Doxygen

```bash
doxygen lab1/Doxyfile
```

Главная страница создаётся из корневого `README.md`. HTML-документация находится в `lab1/docs/html/index.html`. Предупреждения Doxygen настроены как ошибки в CI.

## 6. GitHub: коммит и отправка

```bash
git status
git add .
git commit -m "fix(lab1): align implementation with specification"
git push origin main
```

После push откройте **GitHub → Actions**, выберите workflow `Lab 1 CI` и изучите логи каждого job. Если CI упал, сначала прочитайте конкретный шаг и исправьте причину ошибки, затем отправьте новый коммит.

## 7. Создание релиза

После слияния изменений в `main` создайте версионированный тег:

```bash
git tag v1.0.0
git push origin v1.0.0
```

Workflow соберёт релизный бинарный файл, запустит его smoke-тест в чистом контейнере, опубликует вложения GitHub Release и скачает опубликованный архив для повторной проверки контрольной суммы.

## 8. Как устроен проект

`tic_tac_toe::TicTacToe` владеет динамическим массивом игрового поля и реализует правило трёх. `polynomial::Polynomial` хранит коэффициенты в `std::vector<double>` по возрастанию степени, нормализует старшие коэффициенты и использует временные результаты для сильной гарантии исключений. CLI отвечает за ввод, отображение и меню; домены от него не зависят.

## 9. Сценарии демонстрации

В `lab1/docs/demo/` находятся три сценария ввода и соответствующие файлы с ключевыми ожидаемыми строками. Проверить их локально можно так:

```bash
lab1/scripts/smoke_test.sh lab1/build/bin/lab1_cli
```

## Разбор GitHub Actions для защиты

| Job | Что делает | Зачем он нужен |
|---|---|---|
| `format-lint` | Проверяет форматирование clang-format, выполняет clang-tidy и проверяет стиль/независимость скриптами | Находит несогласованный формат, подозрительные конструкции, нарушения соглашений и архитектурных границ |
| `build-test` | Собирает проект и запускает тесты под GCC и Clang | Проверяет компиляцию разными компиляторами и соответствие поведения требованиям тестов |
| `sanitizers` | Собирает с ASan/UBSan, запускает unit- и smoke-тесты с диагностикой утечек | Ищет ошибки доступа к памяти и неопределённое поведение |
| `coverage` | Собирает с инструментированием, запускает тесты и проверяет покрытие трёх областей | Требует более 90% покрытия строк отдельно для `tic_tac_toe`, `polynomial` и проекта в целом |
| `docs` | Генерирует Doxygen HTML, проверяет наличие обоих классов и загружает документацию как артефакт | Подтверждает наличие машинно-генерируемой документации API |
| `package` | Собирает статический Linux-бинарник, добавляет demo/smoke-файлы, формирует архив и SHA-256 | Готовит проверяемый исполняемый артефакт для преподавателя |
| `smoke-clean-container` | Скачивает собранный артефакт и запускает сценарии в Ubuntu 22.04 без инструментов сборки | Проверяет, что пакет запускается вне среды сборки |
| `release` | Для тегов `v*` публикует архив, контрольную сумму и архив документации в GitHub Releases | Доставляет проверенную версию проекта пользователю |
| `verify-release` | Скачивает опубликованные в Releases архив и SHA256SUMS, проверяет контрольную сумму и запускает сценарии | Подтверждает, что опубликованный файл совпадает с проверенным артефактом и действительно запускается |

## 10. Ограничения проверки

Зелёный CI означает, что перечисленные автоматические проверки прошли для конкретного коммита. Он не заменяет понимание алгоритмов, контрактов классов, исключений и тестов. На защите важно объяснить владение ресурсами в `TicTacToe`, нормализацию и арифметику `Polynomial`, строгую гарантию исключений и разделение доменной логики от CLI.
